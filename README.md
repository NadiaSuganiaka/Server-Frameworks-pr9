# ПР9 · CampusHub · Реєстрація користувача на подію

**Дисципліна:** Розробка серверної частини Web-застосунків. **Група:** КНК-23.
**Тривалість:** окрема пара 90 хвилин. Обов’язкове програмування: 40–45 хвилин. **Максимум: 4 бали.**

## Що потрібно отримати

Один POST зберігає реєстрацію в PostgreSQL. Повтор тієї самої пари не створює другий рядок. Відсутній користувач або подія дає зрозумілу відповідь API.

Ви не створюєте проєкт, модель БД, міграцію чи auth-модуль із нуля. Усе це для цієї роботи підготовлено або винесено за її межі.

## Що вже готово

- Express, TypeScript, Prisma 6.4.1, PostgreSQL; точні залежності в package-lock.json.
- User, Event, Registration; зовнішні ключі й `@@unique([eventId,userId])`.
- Валідація, обробник помилок та scoped mapper P2002 → 409, P2003 → 404.
- Користувачі 2, 3; події 1, 2; маршрути перегляду `/users`, `/events`.
- Готові `requests.http`, Postman collection і команда `npm run check`.

## Перед парою — викладачу

Node.js 22 LTS рекомендовано (мінімум 20.19). У цій автономній заготовці Express 4 / Prisma 6; не треба змінювати залежності вже наявного курсового проєкту. Це незалежний від попередніх робіт стартовий стан B-P09-start, а не твердження про опублікований Git-тег.

1. У каталозі стартера виконати `npm ci`.
2. Скопіювати `.env.example` у `.env` (Windows: `Copy-Item .env.example .env`; macOS/Linux: `cp .env.example .env`).
3. За наявності Docker: `docker compose up -d --wait`. Порт БД — 5549, сервер API — 3001.
4. Виконати `npm run db:prepare`. Або підставити в `.env` адресу **окремої навчальної PostgreSQL БД** та виконати ту саму команду; Docker не обов’язковий.
5. `npm start`, відкрити `http://localhost:3001/health`, `/users`, `/events`. POST до виконання TODO повертає 501 — це очікуваний початковий стан.

Залежності, БД і fixtures мають бути готові до студентської частини. `db:seed` не очищає реєстрації. Для показу 201 потрібна ще не використана пара; якщо (1,2) уже є — використайте (2,3) або окрему нову навчальну БД. Не очищайте загальну таблицю студентів. Ніколи не підключайте цей стартер до робочої БД.

## На початку заняття — студенту

Відкрийте готовий каталог. Якщо залежності й БД підготував викладач, достатньо `npm start`. Не виконуйте міграції/скидання БД повторно. Якщо запуск не вдається, повідомте викладача: налаштування середовища не є основним завданням.

Якщо ви пропустили ПР8, беріть саме цей стартер: усі потрібні передумови вже включені.

## 4 кроки виконання

1. **5 хв:** відкрийте `prisma/schema.prisma`, `/users` і `/events`. Знайдіть унікальну пару та зовнішні ключі. Переконайтеся, що user 2 і event 1 існують.
2. **10 хв:** у `src/registration.repository.ts` замініть TODO B1 однією операцією `prisma.registration.create`. Передайте `eventId`, `userId`; поверніть `id`, `eventId`, `userId`. Репозиторій не повинен отримувати `req/res`.
3. **10 хв:** у `src/registration.controller.ts` замініть TODO B2: дочекайтеся методу репозиторію та поверніть `res.status(201).json(row)`. Готові валідатор, catch та mapper збережіть.
4. **15–20 хв:** виконайте три запити нижче. Потім `npm run typecheck` і `npm run check`. Виправте власні TODO, якщо перевірка повідомляє про відхилення. Самі тести писати не потрібно.

## Очікувані відповіді

```http
POST /events/1/registrations
Content-Type: application/json

{"userId":2}
```

Перший запит на чистій парі: `201`, наприклад `{"id":17,"eventId":1,"userId":2}`. Значення id генерується БД й може відрізнятися.

Той самий запит повторно: `409 {"code":"ALREADY_REGISTERED"}`. Другий запис не створюється.

`POST /events/9999/registrations` з `{"userId":2}`: `404 {"code":"RELATED_RESOURCE_NOT_FOUND"}` за умови, що event 9999 відсутній.

Додаткові готові перевірки: відсутній user → 404; userId як рядок → 400. `npm run check` створює власні тимчасові fixtures і видаляє лише їх, тому його можна запускати повторно, не скидаючи ваші реєстрації. Тест потребує окремої навчальної БД; id 2147483647 зарезервовано як відсутній для перевірки.

## Що здати

Два змінені файли (`registration.repository.ts`, `registration.controller.ts`), три відповіді (201, 409, 404) та заповнений `submission.md`. Достатньо commit або архіву цих файлів із результатами. Не здавайте node_modules, `.env`, базу чи великий звіт.

## Оцінювання — 4 бали

| Критерій | Бал |
|---|---:|
| Одна коректна вставка через репозиторій | 1 |
| Контролер повертає 201 і створений запис | 1 |
| Перевірено 201, повтор 409 і відсутній ресурс 404 | 1 |
| Результат відтворюється; пояснено роль UNIQUE та mapper | 1 |

Робочий POST на цьому занятті — навчальний сценарій. userId з тіла не підтверджує особу; автентифікацію та права тут не додаємо. Не розгортайте приклад як публічний API.

## Розклад 90 хвилин

20 хв — вступ, запуск, демонстрація; 45 хв — виконання; 25 хв — перевірка, запитання, пояснення, здача. Для швидших: пояснити, чому pre-check без UNIQUE не захищає від двох одночасних запитів. Необов’язкове завдання не впливає на максимум основної частини.
